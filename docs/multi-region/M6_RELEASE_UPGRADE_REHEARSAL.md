# M6 — published v0.4.5 → working-tree application-led upgrade rehearsal

**Local, bounded, synthetic rehearsal. No production data, GitOps sync, Helm install or canary was touched.** The [public latest release](https://github.com/fiztoz/uptime-phoenix/releases/tag/v0.4.5) on 2026-09-29 was `v0.4.5`; its chart uses image tag `0.4.5` (without the `v`). Confirm the operator's *actual* deployed tag before relying on this as a matching baseline.

## Reproduce

```sh
# One-time only if not already cached: public release image, linux/arm64 or linux/amd64.
docker pull ghcr.io/fiztoz/uptime-phoenix:0.4.5
python3 -B scripts/m6_release_upgrade.py
```

The script refuses a remote Docker socket and uncached images/modules, requires an already installed local Go toolchain satisfying `go.mod`, and creates a **new private Docker network**, three disposable containers and a new MariaDB 11 database **without a published DB port or host volume**. To match the operator's in-release MariaDB topology, it uses database `phoenix`, an ephemeral non-root application user/password, and the chart's UTF-8 collation, UTC server clock and buffer-pool flags. The password exists only for this disposable database and is never printed. The application ports are randomly bound to `127.0.0.1` for readiness and synthetic API checks. No caller DSN, credential or existing container is read or modified. It removes its own containers and network and fails if any remain. The downloaded release image is a cache item, not a test container or database; remove it after the rehearsal if nothing else uses it.

1. Run the **actual published 0.4.5 all-in-one arm64 image** and require readiness after its own `repository.RunMigrations` applies `001`–`034`. Register an ephemeral admin through the release API. Insert 100 disabled monitors in the *release schema* and 100,000 synthetic legacy heartbeats across two real monthly partitions, plus 1,000 rows each in 1m/1h/1d rollups. Confirm the release serves those monitors through its authenticated API.
2. Stop the release process; build the working-tree `cmd/app` as a CGO-free Linux binary (`GOPROXY=off`) and run it in the same distroless nonroot base against **the same database**. Require readiness and a migration ledger of 74 (`035`–`074` applied by the application), compare all historic row counts and identity aggregates, monthly partition names, four sampled heartbeat rows, and all three rollup counts/ID sums. Require every legacy heartbeat's `probe_id` to be `local`.
3. Log in with the old admin on the upgraded application and fetch the same 100 monitors. Verify the new regional unique index `(monitor_id,probe_id,bucket)` on all three rollups, then insert a *remote* row into the same old bucket without overwriting a local row or reusing its ID. Restart the new application; require the migration ledger and all resulting data to remain unchanged (idempotent startup).

## Limits / handoff to the operator

This fills the gap in [the earlier rehearsal](M6_MIGRATION_RUNNER_REHEARSAL.md): those runs applied `001`–`037` as SQL with a backfilled ledger; **this run starts the published 0.4.5 application itself**, then upgrades with the new application, on preserved data. It still uses only 100,000 synthetic rows—not a representative production-sized copy or true peak-disk/lock sampling. The Helm chart is only locally at version `0.4.5`; **no newer packaged chart/image was built or published** in this rehearsal. It does not prove an Argo CD sync, credential/probe backup, full section-13 matrix, load envelope or canary. An operator should take and verify the UI backup, establish an approved restore path for the actual PVC/database, deploy an actual new tagged release through GitOps, observe migrations and health, and execute the canary/recovery steps. Do not downgrade the executable against an upgraded database; use the operator's verified backup/restore procedure if rollback is required.
